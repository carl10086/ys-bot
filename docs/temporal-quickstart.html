Temporal Quick Start —— ys-bot 视角

读者预设：资深后端工程师，第一次接触 durable execution · 目标：理解 Temporal 在 ys-bot 里的角色、调用方式、崩溃恢复机制

一句话：Temporal 让你的函数调用有记性——每一步（activity）完成后，结果被写进它自己的 PostgreSQL（event history）；进程死了，新进程读 PG 里的记录，从断点接着跑。

§1是什么（mental model）

Temporal server 本质上就是无状态服务层 + 一个 PostgreSQL。它从不执行你的代码——你写的 workflow / activity 全部跑在你自己的进程（ys-worker）里。Temporal server 只做两件事：

  • 派活：把待执行的 workflow / activity 任务分发给轮询中的 worker；
  • 记账：把每一步的结果写进 PG，形成 event history——这是整个系统执行进度的唯一真相。

三个角色

ys-bot 的运行时由三个角色组成，其中两个是我们自己的 Go 二进制，一个是 Temporal：

角色是什么有状态吗职责
ys-server 我们的 Go 二进制①（HTTP API + 内嵌 SPA） 无状态 门房：收浏览器消息、写 Redis 队列、启动 workflow、推"有变化"信号
Temporal server 独立服务（docker-compose 起）+ PG 服务无状态，真相在 PG 调度员 + 记事本：派活、记账、闹钟
ys-worker 我们的 Go 二进制② 无状态 agent 本体：跑 TurnWorkflow 的代码，轮询领活

核心概念

概念含义
Workflow一个多步骤过程，例如一个 turn（用户发一条消息到 agent 给出回复的完整循环）
Activityworkflow 中的一步；所有碰外界的操作（读 Redis、调 LLM、调 VM）都在 activity 里
Task QueueTemporal 内部分配任务的队列；worker 按队列名轮询领活
Event HistoryPG 里的账本：每个已完成的 activity 的输入输出都记在这里
Replay重放：恢复时函数从头跑，但已完成的 activity 短路返回历史结果，不真实执行
Signal往一个正在运行的 workflow 里发消息（如"用户又发来一条"、"批准了这个操作"）
Durable Timer闹钟；worker 全挂也照响——因为它记在 PG 里，由 Temporal server 触发

架构总图与关键事实

关键架构事实
  • ys-server 和 ys-worker 从不直接通信，一次 RPC 都没有；所有协调都经过 Temporal + Redis。
  • worker 是主动轮询领活，不是 server 推送 → worker 可以随便重启、随便扩容。
  • 整个系统只有三处有状态：PG（执行进度）、Redis（业务状态）、VM 快照（环境）。进程全部无状态。

§1.5ys-server 怎么"调用" Temporal

Qys-server 居然就是简单调用一下？需要部署一个独立的服务去调用 Temporal 吗？

不需要任何独立服务——Temporal 的 client 就是一个普通 Go 库（go.temporal.io/sdk/client），import 进 ys-server 就完事。类比：ys-server 连 Redis 用的是 go-redis 库，连 Temporal 用的是 temporal client 库，两者是同等级别的东西——一个带连接池的 RPC 客户端。需要独立部署的是 Temporal server 本身（docker-compose 里的一条），而不是"调用方"。

ys-server 处理"用户发消息"的完整逻辑就这些：

ys-server / handle_send.go伪代码
// ys-server 里处理"用户发消息"的 handler
func handleSend(w http.ResponseWriter, r *http.Request) {
    msg := parse(r)                          // {id: uuid, session: s1, text: "..."}

    // ① 幂等去重（s16 Sending：唯一 ID 让重试安全）
    if !redis.SetNX("msg:seen:"+msg.ID, 1, 24h) {
        return OK("duplicate dropped")
    }
    // ② 消息落库 + 进会话队列（s16 The turn）
    redis.RPush("session:"+msg.Session+":queue", msg)

    // ③ 若该会话当前没有在跑的 turn，启动一个 TurnWorkflow
    if redis.SetNX("session:"+msg.Session+":active", 1, 10min) {
        temporalClient.ExecuteWorkflow(ctx,            // ← 就是一次 RPC
            workflowOptions{WorkflowID: "turn-"+uuid, TaskQueue: "agent"},
            TurnWorkflow, TurnInput{SessionID: msg.Session})
    }
    return OK()                              // 全程 <10ms
}

ExecuteWorkflow 的本质：向 Temporal server 发一个 RPC，效果约等于往 PG 写一行"这个 workflow 该跑了"。之后 ys-server 与这件事再无关系——不持有连接、不等结果、不知道 agent 想了什么。回复的送达走另一条路（Redis → SSE，见 §4）。

ys-server 对 Temporal 的全部操作就四类：

操作作用ys-bot 里的用法
ExecuteWorkflow启动一个 workflow会话空闲时收到新消息 → 启动 TurnWorkflow
SignalWorkflow往跑着的 workflow 发消息"用户又发来一条"、"批准了这个操作"
QueryWorkflow查 workflow 当前状态调试用（业务状态在 Redis，正常不走这条）
CancelWorkflow取消一个 workflow用户打断当前 turn

§2怎么做（机制：event history + replay）

先看 ys-worker 里注册的真实代码形状。一个 turn 的 agent loop 就是 TurnWorkflow：

ys-worker / turn_workflow.go伪代码
func TurnWorkflow(ctx workflow.Context, in TurnInput) error {
    // 每个 ExecuteActivity 完成时，Temporal server 自动把结果写进 PG
    state := workflow.ExecuteActivity(ctx, LoadSession, in.SessionID)   // 从 Redis 读会话
    reply := workflow.ExecuteActivity(ctx, CallLLM, state, in.Messages) // 调模型（花钱的）
    for reply.HasToolCalls() {
        result := workflow.ExecuteActivity(ctx, ExecTool, reply.Tool)   // Connect-RPC 调 VM agentd
        reply   = workflow.ExecuteActivity(ctx, CallLLM, state, result)
    }
    return workflow.ExecuteActivity(ctx, SaveReply, reply)              // 回复落 Redis + 发"changed"信号
}
ys-worker / main.goworker 注册
w := worker.New(temporalClient, "agent", worker.Options{})
w.RegisterWorkflow(TurnWorkflow)
w.RegisterActivity(LoadSession); w.RegisterActivity(CallLLM)
w.RegisterActivity(ExecTool);    w.RegisterActivity(SaveReply)
w.Run() // 内部：长轮询 Temporal server 领活

event history：PG 里的账本

正常跑一个"汇总 csv"的例子时，PG 里会长出这样的记录：

Event 1: WorkflowStarted      (input: session=s1)
Event 2: ActivityScheduled    (LoadSession)
Event 3: ActivityCompleted    (LoadSession, result={会话历史…})
Event 4: ActivityScheduled    (CallLLM)
Event 5: ActivityCompleted    (CallLLM, result="我要exec ls")   ← 模型结果也记下了
Event 6: ActivityScheduled    (ExecTool, ls ~/downloads)
Event 7: ActivityCompleted    (ExecTool, result="a.csv b.csv")
…
关键只有完成的 activity 才入账。这是理解恢复机制的全部前提：账本里没有完成记录的步骤，就是恢复后要真正重做的步骤。

replay：代码"快进"到断点

恢复时，新 worker 拿到这个 workflow，从头执行 TurnWorkflow 的函数代码——但每个 ExecuteActivity 调用先查账：

  • 账上有 ActivityCompleted → 直接返回历史结果，不真实执行（LLM 不重调，钱不重烧）；
  • 账上没有完成记录 → 才真正派活执行，完成后补记到账上。

从函数视角看，代码就像"快进"到了断点：前面的步骤瞬间返回旧值，第一个没记账的步骤才真正跑。

代价确定性约束：workflow 函数里不能碰网络 / 时钟 / 随机数——这些全部得放进 activity。否则重放时两次执行结果不一致，账本就对不上了。这也是 TurnWorkflow 里每一行都是 ExecuteActivity 的原因：workflow 只编排，activity 才碰世界。

§3为什么（设计动机）

agent 的 turn 完美符合 durable execution 的三个目标特征：

  • 多步骤：model ↔ tools 循环，一个 turn 少则两三步、多则几十步；
  • 长时间：几分钟是常态，远超一次 HTTP 请求的生命周期；
  • 怕崩溃：LLM API 本身就抖，而且每次调用都烧钱——重来一遍不只是慢，是贵。

家谱上，Temporal 源自 Uber 的 Cadence——打车行程是天然的长流程（接单 → 行程中 → 支付 → 评价，跨几小时、跨无数进程重启）。同族产品：AWS Step Functions、Azure Durable Functions、Restate。它们解决的是同一类问题：多步骤、长时间、怕崩溃的过程，怎么在"进程随时会死"的现实里可靠跑完。

四种架构，worker 崩溃时各损失什么

架构长流程怎么放worker 崩溃时
单体全在一个进程内存里全死，进度随进程蒸发
微服务 RPC步骤散在多个服务的调用栈里进度归零——调用栈没了，没人记得跑到哪
消息队列步骤间用消息传递从头再来——消费位点只记到步骤粒度，步骤间状态自己想办法
durable execution一个函数写到底，进度自动入账断点续跑——重放函数，已完成步骤短路返回

不用 Temporal，要手写什么

能力手写版本长什么样
每步进度存取 + 重放逻辑自己设计 checkpoint 格式、存取时机、恢复时按状态机跳转——每个 workflow 类型一份
VM 休眠闹钟e2b 那个 50ms 轮询 Redis zset 的 evictor—— Temporal 的 durable timer 一条调用替代
LLM 429 重试循环 + 状态机每个 activity 自己写重试/退避，崩溃后还得知道"重试到哪一步了"
每步可观测埋点自己打日志/指标——Temporal 的 event history 天然就是完整的执行审计

Temporal 把这四行全给了。这不是"少写代码"的问题，是这些基础设施代码一旦手写，每个 bug 都直接换算成线上事故。

§4实际例子（完整走查）

场景：用户在浏览器里发"帮我把 downloads 里的 csv 汇总一下"，此时 VM 处于休眠状态。

正常流程时序

━━━ ys-server 的部分（<10ms）━━━
浏览器 POST /send → SETNX msg:seen:{uuid} 去重 → RPush session:s1:queue
→ 无 active turn → ExecuteWorkflow(TurnWorkflow) → 返回 200
（ys-server 责任到此结束）

━━━ Temporal server（只记事）━━━
记下 workflow 待执行 → 派给轮询中的 ys-worker

━━━ ys-worker（agent loop，几分钟）━━━
LoadSession（读 Redis 历史+队列消息）
→ CallLLM（模型说"我要 exec"）
→ ExecTool（Connect-RPC → VM agentd 跑 shell；VM 睡着 → 先 ResumeVM 唤醒）
→ CallLLM（模型给出汇总结论）
→ SaveReply（回复写 Redis + INCR seq + PUBLISH "changed"）
→ workflow 完成

━━━ 浏览器怎么看到的 ━━━
ys-server 的 SSE 收到 Redis "changed" → 推给浏览器
→ 浏览器 GET /messages?after=42 → ys-server 从 Redis 读 → 显示

注意最后一段：回复的送达不经过 Temporal。Temporal 管"agent 干活"的过程可靠性；浏览器看到结果走的是 ys-server 已有的 Redis → SSE → 拉取通道。两条路各司其职。

恢复走查：ys-worker 中途被 OOM 杀掉

假设 ys-worker 在 CallLLM 完成后、ExecTool 执行前被杀：

PG 账目停在 Event 5（CallLLM 已完成，ExecTool 还没跑）
Temporal server 发现 workflow 没结束、worker 没心跳 → 派给新 worker
新 worker 重放 TurnWorkflow：
  ExecuteActivity(LoadSession) → 查账有 Event 3 → 返回旧结果（没真跑）
  ExecuteActivity(CallLLM)     → 查账有 Event 5 → 返回 "我要exec ls"
                                 ★ 模型没有重调，钱没重烧 ★
  ExecuteActivity(ExecTool)    → 没有完成记录 → 真正执行
  …继续到结束

对用户来说，只是这个 turn 慢了几秒。对系统来说，一次进程崩溃被完全消化，无任何人工介入。

各种死法对照表

谁挂了损失恢复方式
ys-server无客户端重试 + msg ID 幂等（SETNX 去重挡掉重复投递）
ys-worker（activity 之间）无新 worker 重放，从断点继续
ys-worker（activity 中途）这一步重做activity 重试 + 幂等键——ls 跑两次无害，"发邮件"不行：有副作用的 activity 必须带幂等键
Temporal server无无状态重启，从 PG 读回一切
VM环境重置快照恢复；会话状态反正不在 VM
PG唯一真事故备份——整个系统唯一的命门
收尾洞察整个系统的容错设计，本质是把"怕丢的东西"收敛到尽量少的存储里——PG（执行进度）、Redis（业务状态）、VM 快照（环境）——然后让所有进程保持无状态。进程谁死都无所谓，存储只有三处需要认真对待。故障被设计成了日常。
