## 目标与验收

**目标**：agent 从"只会聊天"变成"有手"——LLM 决定调工具，命令在**真 microVM** 里执行，结果回到对话。

**验收标准**（对应 phasing.md M2 行）：

1. SPA 发"看看你 /etc 下有什么"→ agent 调 shell 工具 → 命令在 Firecracker microVM 里执行 → `tool_call` / `tool_result` / `assistant` 三条消息按序回显
2. 同一用户第二条消息再用工具，VM 不重建（复用醒着的 VM）
3. worker 重启后，进行中的 turn 由 Temporal 恢复，不丢工具结果

**明确不做**（M2 边界）：Browser/Desktop/截图（需虚拟屏幕）、快照休眠恢复（M4，但接口预留）、PTY/流式 stdin（envd 的 Connect/StreamInput）、多用户隔离加固（auth token）。

## 从 e2b 借鉴什么（对照表）

| e2b 组件 | 它的职责 | ys-sandbox 对应物 | 借鉴程度 |
|---|---|---|---|
| `envd`（VM 内守护进程） | Connect-RPC：process/filesystem 服务 + HTTP 控制面 | **agentd** | 协议形状照抄，方法集砍到 4 个 |
| `orchestrator/pkg/sandbox/fc` | Go 封装 firecracker API socket（进程/config/内核参数/MMDS） | **vmdriver 的 FC 实现** | 抄职责划分（VM 生命周期管理在宿主侧 Go 代码里），不抄代码（它太深） |
| `orchestrator/pkg/sandbox/network` | 每沙箱一个 slot：veth 对 + tap + slot IP，orchestrator 经 slot IP 访问 envd | **vmdriver 的网络部分** | 照抄模型，实现砍到最小（IP 池 + tap + NAT，无 TC 限速无防火墙） |
| envd 烤进模板镜像 | 构建模板时装好 envd + init 拉起 | **rootfs 构建脚本** | 照抄：agentd 静态二进制 + init 脚本打进 rootfs |
| `/init` 控制面（启动后同步 env/workdir/token） | 每 VM 启动后第一次调用 | **agentd 的启动参数** | 简化：M2 单用户，env/workdir 用启动参数写死，不要 /init 接口 |
| MMDS（169.254.169.254 元数据注入） | 给 guest 传元数据 | — | **不抄**：M2 元数据量小，agentd 启动参数够 |
| nomad 调度、template 构建流水线、client-proxy、auth | 生产多租户基建 | — | **不抄** |

## 拓扑决策：薄 vmhostd 上宿主，ys-worker 留在 Mac（2026-10-29 评审定案）

约束：firecracker API 是宿主本地 unix socket，**管 VM 必须在 VM 所在机器上**（e2b orchestrator
存在的理由）。但 ys-worker 是 durable workflow 的大脑，不该兼任宿主运维——分层原则是
**大脑（worker）与手脚的管家（vmhostd）分开**。

```
Mac (开发机)                              腾讯云 152.136.212.59 (VM 宿主)
─────────────────                        ──────────────────────────────────
ys-server :8080  ←── SPA
PG/Redis/Temporal (docker)
ys-worker（GoLand 断点调试回路不变）── Connect-RPC over 公网 ──→ vmhostd
  ├─ 编排：Temporal activities                 ├─ 管 firecracker 进程生命周期
  └─ vmdriver = vmhostd 的 RPC client          └─ agentd 反向代理 ──→ microVM tap IP:4998
```

- **vmhostd**（`cmd/vmhostd`）：哑基础设施，零 LLM/workflow 逻辑。两个职责：
  ① VM 生命周期（建/毁/状态/快照，vmdriver 的 FC 实现住这里）
  ② agentd 反向代理（worker 的 Exec/ReadFile/WriteFile 经它转进 VM）
- **为什么 VM 不能靠公网 IP 直连**：公网 IP 是宿主网卡的；VM 在宿主内核的私有 tap 网段
  （10.200.x.x），公网不承运、宿主不转发。直连要么每 VM 烧一个公网端口做 DNAT
  （agentd M2 无鉴权 = 命令执行口直接暴露公网），要么买 EIP。vmhostd 代理 = 全宿主一个
  受控入口，鉴权将来只加一个点（e2b 的 client-proxy 同角色）。
- **GoLand 调试回路不变**：worker 留在 Mac，M1 的断点学习法延续。

### 分布式目录与健康探测（e2b 实证：Redis）

e2b 的答案（`packages/shared/pkg/sandbox-catalog`）：**sandbox → 宿主的映射放 Redis**，
任何机器要联系某 sandbox，先查 catalog 拿到 orchestrator 地址再直连。我们照抄形状：

| 键 | 内容 | TTL | 写入方 |
|---|---|---|---|
| `vmhost:alive:{host_id}` | vmhostd 心跳（endpoint + 时间） | 30s，心跳续期 | vmhostd |
| `sandbox:host:{sandbox_id}` | sandbox 落在哪个 host_id | VM 销毁时删 | vmhostd |

- 健康探测两层：vmhostd `/health`（进程活着）+ 心跳 key 过期（真死了 catalog 自动失效）
- 红线一致：catalog 是**可丢协调态**——丢了重建（VM 活着，vmhostd 重注册）；
  PG `sandboxes` 表仍是事实源
- M2 单宿主时这两个键各只有一条，但**读写路径从第一天就按分布式写**——
  worker 不记任何宿主地址，永远先查 catalog。"其他机器唤起 VM 测试" = 查 catalog
  → 直连对应 vmhostd，天然支持

### 宿主亲和性（2026-10-29 评审补充）

- 编排 activity（CallLLM/写 messages）无状态任意扩；VM activity 经 catalog 路由到
  正确宿主的 vmhostd——不需要 Temporal per-host queue 了，**路由问题由 Redis catalog
  在 RPC 层解决**，比 sticky queue 简单（2026-10-29 评审修订，原 per-host queue 方案作废）
- Temporal server 单机 docker 不是多用户生产形态——部署问题（集群/Temporal Cloud），
  与 workflow 模型无关；每 turn 一个 workflow 正是其设计甜区

## 组件设计

### 1. vmdriver（两侧：`internal/vmdriver` + vmhostd 进程）

接口不变，但实现拆成两半——**worker 侧是 RPC client，FC 实现住 vmhostd**：

```go
// worker 侧：对上层只承诺"给我 agentd 调用通道"。实现可换（Remote / Docker / mock）。
type Driver interface {
    EnsureAwake(ctx context.Context, sb store.Sandbox) (Client, error)  // Client = agentd 调用通道
    Status(ctx context.Context, sandboxID uuid.UUID) (string, error)
    // Sleep / ResumeFromSnapshot: M4 加，接口现在不定义（避免空设计）
}
```

- **worker 侧 RemoteDriver**：查 Redis catalog → Connect-RPC 调 vmhostd；Exec/ReadFile/WriteFile 经 vmhostd 代理
- **vmhostd 侧 FC 实现**（对照 e2b `fc/` + `network/` 的砍版）：
  - **VM 布局**：每 sandbox 一个目录 `/data/firecracker/vms/<sandbox_id>/`（fc.sock、rootfs.ext4、log）
  - **创建**：`cp --reflink=auto` 从模板 rootfs 复制 → 建 tap → firecracker API 配 boot-source（共用 vmlinux-pvm）/drives/network/machine-config（1 vCPU/512MB）→ InstanceStart → 轮询 agentd `/health` 直到通 → 写 catalog
  - **网络**（e2b slot 模型砍版）：每 VM 一个 tap + 固定池 IP（`10.200.{slot}.2/30` 对 `10.200.{slot}.1`），宿主一条 iptables MASQUERADE 出公网。一次性宿主初始化脚本 `setup-host-net.sh`；slot 分配 = sandboxes 表加 `slot int` 列，单行计数器发号
  - **代理**：收到 Exec/ReadFile/WriteFile → 按 sandbox_id 查本机 VM 的 tap IP → 转发给 agentd → 回传
  - **清理**：VM 进程死了 / sandboxes 行删了 → 回收 slot、删 tap、删目录、清 catalog

### 2. agentd（VM 内守护进程，`cmd/agentd`，Connect-RPC）

```proto
// 砍自 envd 的 process + filesystem，只留 M2 所需
service Agentd {
  rpc Health(HealthRequest) returns (HealthResponse);
  // 同步执行：跑完返回。对应 envd process.Start 的"等到结束"用法；
  // envd 的流式 Start/Connect/PTY/SendSignal 留作 M3+ 参照，先不实现
  rpc Exec(ExecRequest) returns (ExecResponse);
  rpc ReadFile(ReadFileRequest) returns (ReadFileResponse);
  rpc WriteFile(WriteFileRequest) returns (WriteFileResponse);
}

message ExecRequest  { string cmd = 1; string workdir = 2; map<string,string> env = 3; uint32 timeout_sec = 4; }
message ExecResponse { int32 exit_code = 1; string stdout = 2; string stderr = 3; }
message ReadFileRequest  { string path = 1; }
message ReadFileResponse { bytes content = 1; }
message WriteFileRequest { string path = 1; bytes content = 2; }
message WriteFileResponse {}
```

- **静态编译**（`CGO_ENABLED=0`），rootfs 里就一个二进制 + init 脚本拉起，监听 `:4998`
- envd 里值得记住、M2 先不做的：流式 stdout（Start 返回 stream）、PTY、ListDir/WatchDir、/init 控制面、access token 鉴权、/metrics

### 3. rootfs 构建脚本（`scripts/build-rootfs.sh`，手工跑一次）

借鉴 e2b"envd 烤进模板"：在现有 bionic rootfs（冒烟用的那份）基础上，mount loop 挂进去 → 放 agentd 二进制 + systemd unit/init 脚本 → 卸载。产出 `rootfs-agentd.ext4` 当模板。e2b 的模板流水线（template-manager + 构建编排）不抄——我们一个用户一个模板，脚本够了。

### 4. turn loop 工具分支（`internal/agent` + `internal/workflow`）

- **工具定义**：M2 只注册一个 tool：`shell`（→ agentd.Exec，经 vmhostd 代理）。工具 schema 定义在 server（讲座 s19：工具定义与调度在 server）；更多工具跑通后参考 envd/aider/codex 再加
- **loop 形状**（CallLLM activity 循环，全部在 TurnWorkflow 内）：
  1. CallLLM → 若回复无 tool_calls → 写 assistant 消息 → 结束
  2. 有 tool_calls → **首个 tool_call 前先 EnsureAwake**（讲座 s11 懒恢复：纯对话 turn 全程不碰 VM）→ 逐条经 agentd 执行（ExecTool activity）
  3. 每步写 messages：`tool_call`（参数）+ `tool_result`（结果）→ PublishChanged → 带着结果继续 CallLLM
- **防护**：单 turn 工具调用上限（如 20 次）防 loop 失控；Exec 默认 timeout 60s

### 5. 数据模型改动（沿用统一建表约定）

- `sandboxes` 表启用（schema 已有）：新增 `slot int UNIQUE`（tap IP 池发号，父行计数器模式——没有父表，用单行计数器表或 `SELECT max(slot)+1` 串行化在 EnsureAwake 事务里；M2 并发=1，先简单）
- `sandboxes.vm_ip` 存 `10.200.{slot}.2:4998`；`status` ∈ creating/awake/stopped/failed
- messages 的 `kind` 已有 tool_call/tool_result，无改动
